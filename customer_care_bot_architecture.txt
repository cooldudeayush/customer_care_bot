================================================================================
  1. THE CORE IDEA (recap, so the architecture has a north star)
================================================================================

This is NOT a chatbot that TELLS customers how to solve problems.
It is a care agent that RESOLVES problems by taking real actions.

Clichéd bot : "To get a refund, please go to Orders > Returns and..."
This bot     : "I've checked order #1234 — it's within the 30-day window, so
                I've issued your refund of Rs.1,499. You'll see it in 3-5 days.
                Anything else?"

Five differentiators, in priority order:
  1. AGENTIC RESOLUTION  — the bot calls tools to actually DO things.
  2. EMOTIONAL ADAPTATION — detects frustration/confusion, modulates tone.
                            (NOT "always cheerful" — adaptive, which is smarter.)
  3. GROUNDED + UNCERTAINTY-AWARE — never invents a policy; says "let me check".
  4. CROSS-SESSION MEMORY — remembers the CUSTOMER, not just the chat.
  5. GRACEFUL ESCALATION — knows its limits; hands off WITH a full summary.

Plus: Hinglish / code-switching support (regional languages = future scope).

CRITICAL FREE-TIER CONSTRAINT (drives the design):
  Gemini free tier ≈ 15 requests/minute. A naive turn that makes 5 separate LLM
  calls (classify emotion, classify intent, pick tool, generate, summarize) caps
  you at ~3 user turns/minute and WILL throttle during a live demo.
  -> MITIGATION (build this in from the start):
     - Collapse perception into ONE structured call: a single Gemini call using
       function-calling / JSON mode that returns {emotion, intent(s), entities,
       tool_decision} together.
     - That's ~2 LLM calls per turn (perceive+decide, then generate) instead of 5.
     - Add exponential backoff on 429 errors (1s, 2s, 4s, 8s).
     - Cache embeddings; don't re-embed the doc corpus every run.


================================================================================
  4. COMPONENT-BY-COMPONENT BREAKDOWN
================================================================================

[A] CLIENT / UI LAYER
    - Chat window with message bubbles, streaming token-by-token output.
    - Typing indicator while the agent loop runs (sells the "human" feel).
    - Subtle UI signals: a small "resolving..." state when a tool is firing,
      a "handing you to a specialist" state on escalation.
    - Optional: a side panel showing what the bot "knows" about you (pulled from
      memory) — great demo eye-candy and reinforces the relationship angle.

[B] ORCHESTRATION LAYER (FastAPI)
    - One main endpoint: POST /chat  {session_id, customer_id, message}
    - Loads conversation state + customer memory, runs the agent loop, returns
      the response (stream if possible).
    - Stateless: rehydrates everything from stores on each call.

[C] AGENT LOOP  (detailed in Section 7)
    - The controller. Sequences perception, retrieval, decision, action,
      response, memory update. Implemented as a LangGraph state machine or a
      plain async function.

[D] EMOTIONAL ADAPTATION LAYER
    - Input: latest user message + short recent history + sentiment trend.
    - Output: an emotional read {state: angry|frustrated|confused|neutral|happy,
      intensity: 1-5} plus a TONE DIRECTIVE injected into the generation prompt.
    - Tone policy (examples):
        angry/frustrated -> calm, apologetic, concise, lead with the fix, no
                            cheerfulness, acknowledge the frustration first.
        confused         -> patient, slow, step-by-step, define jargon, offer
                            to do it for them.
        neutral          -> warm, efficient, friendly.
        happy            -> match the energy, brief, positive.
    - Implementation: fold the emotion read into the single structured
      perception call (don't spend a separate LLM call on it — see free-tier
      constraint). The tone directive is just a few lines appended to the system
      prompt for the generation step.
    - This is your instinct ("stress-free, human") done the sophisticated way.

[E] KNOWLEDGE / RETRIEVAL LAYER  (the hybrid "RAG") — see Section 6 for schema
    Two retrieval sources, used together:

    E1. DOCUMENT GRAPH (LightRAG) — unstructured knowledge
        - Corpus: policy docs, FAQs, product manuals, troubleshooting guides.
        - LightRAG builds an entity-relationship graph + vector index over these.
        - Dual-level retrieval: low-level (specific facts) + high-level
          (thematic / multi-hop questions). Handles "compositional" questions
          that flat vector RAG fumbles.
        - Answers: "What is the refund policy for electronics?"

    E2. CUSTOMER OPERATIONAL GRAPH (Neo4j) — structured, live business state
        - Nodes: Customer, Order, OrderItem, Product, Payment, Ticket, Policy.
        - Edges model the customer's actual situation (see Section 6).
        - The agent TRAVERSES this to reason about THIS customer.
        - Answers: "Does customer C's order #1234 qualify for that policy?"

    WHY BOTH (this is the showcase sentence):
       "Your order #1234 contains item X, purchased 12 days ago — within our
        30-day window — so yes, I can refund it now."
       That requires: graph traversal (order->item->date) [E2]
                     + policy retrieval (the 30-day rule)  [E1]
                     + a tool call (issue refund)          [Section 8].
       No single technique does all three. The combination is the architecture.

[F] DECISION ENGINE
    - Decides, per turn, the action type:
        ANSWER    -> respond from retrieved knowledge (no side effects)
        ACT       -> call one or more tools (agentic resolution)
        CLARIFY   -> ask a follow-up (missing info / ambiguous)
        CONFIRM   -> ask permission before an irreversible action
        ESCALATE  -> hand off to a human
    - Driven by the structured perception output. For ACT, it also extracts the
      tool name(s) and arguments.
    - Handles MULTI-INTENT: "return this AND change my address AND when's my
      refund" -> a list of actions, executed in sequence, then one combined reply.

[G] TOOLS / ACTIONS LAYER (agentic resolution) — see Section 8
    - The functions the bot can call. Each is a real (mock) business operation.
    - Backed by mock biz APIs over a seeded SQLite DB. Every action also writes
      back to the Neo4j customer graph (e.g., a refund flips an order's status).

[H] MEMORY LAYER
    H1. SHORT-TERM (within a session)
        - Full conversation transcript + a structured running state
          (open intents, entities mentioned, actions taken this session).
        - Gemini's 1M context can hold the raw transcript easily, but ALSO keep
          the structured state so the agent doesn't re-derive it each turn.
    H2. LONG-TERM (across sessions) — the "remember the customer" feature
        - On session end (or periodically): summarize the session
          (issue, resolution, sentiment, unresolved items, preferences) and
          store it against the customer_id in Postgres.
        - On session START: load the customer's memory and inject a brief
          "what we know about this customer" block into the system prompt.
        - Enables: "Last time you reached out about a delayed order — did that
          get sorted?" This is the session->relationship upgrade.

[I] ESCALATION / HANDOFF LAYER
    - Triggers: tool failure, repeated dissatisfaction, out-of-scope request,
      explicit "I want a human", high anger intensity that isn't resolving.
    - On trigger: generate a HANDOFF PACKET = {customer summary, issue,
      conversation summary, actions already taken, suggested next step,
      current sentiment}. Route it to a (mock) human dashboard or emit it as a
      ticket. The customer NEVER re-explains.
    - Showing the bot knows when NOT to act is a maturity signal judges respect.

[J] GUARDRAILS / GROUNDING LAYER — see Section 9
    - Confirmation gates before money/irreversible actions.
    - "I don't know -> let me check / escalate" instead of hallucinating.
    - PII handling, input validation, tool-failure fallbacks.

[K] OBSERVABILITY / LOGGING
    - Log a structured TRACE per turn: perception output, retrieval hits,
      decision, tools called + results, final response, latency, token counts.
    - Doubles as: debugging aid + demo artifact + evidence of clean engineering
      for the Documentation score.

================================================================================
  6. DATA MODEL
================================================================================

6.1 CUSTOMER OPERATIONAL GRAPH (Neo4j) — node/edge schema
-----------------------------------------------------------
NODES (with sample properties):
  Customer   {id, name, tier(regular|premium), language_pref, lifetime_value}
  Order      {id, date, status(placed|shipped|delivered|cancelled|refunded),
              total, channel}
  OrderItem  {id, qty, price, return_status}
  Product    {id, name, category, price, warranty_days}
  Payment    {id, method, amount, status}
  Ticket     {id, subject, status(open|resolved|escalated), sentiment, created}
  Policy     {id, name, type(refund|return|warranty|shipping), window_days, rules}

EDGES:
  (Customer)-[:PLACED]->(Order)
  (Order)-[:CONTAINS]->(OrderItem)
  (OrderItem)-[:OF_PRODUCT]->(Product)
  (Order)-[:PAID_WITH]->(Payment)
  (Customer)-[:RAISED]->(Ticket)
  (Ticket)-[:ABOUT]->(Order)
  (Product)-[:GOVERNED_BY]->(Policy)
  (Order)-[:REFUNDED_BY]->(Payment)   // created when a refund tool runs

EXAMPLE REASONING QUERY (Cypher) — "can I refund item X on order 1234?":
  MATCH (o:Order {id:'1234'})-[:CONTAINS]->(i:OrderItem)-[:OF_PRODUCT]->(p:Product)
        -[:GOVERNED_BY]->(pol:Policy {type:'refund'})
  RETURN o.date, p.name, pol.window_days
  // The agent compares (today - o.date) to pol.window_days to decide eligibility.

6.2 DOCUMENT CORPUS (LightRAG)
-----------------------------------------------------------
  - Plain text / markdown files: refund_policy.md, shipping_faq.md,
    product_troubleshooting.md, returns_guide.md, warranty_terms.md.
  - Ingest once at startup; LightRAG builds + persists its graph + vector index.
  - Keep this corpus small and clean for the demo — quality over volume.

6.3 MEMORY STORE (Postgres / Supabase)
-----------------------------------------------------------
  TABLE conversations (session_id, customer_id, started_at, ended_at, transcript)
  TABLE customer_memory (customer_id, summary, preferences, open_items,
                         sentiment_history, last_interaction)
  TABLE turn_traces (id, session_id, turn_no, perception, decision, tools,
                     response, latency_ms, tokens)  // observability

6.4 MOCK BUSINESS DB (SQLite) — what the tools actually read/write
-----------------------------------------------------------
  Mirrors the graph's operational data in tabular form for the mock APIs:
  orders, order_items, products, payments, tickets. Seed it with 5-10 realistic
  customers and orders so the demo has something to act on.


================================================================================
  7. THE AGENT LOOP (the heart) — what happens on every user turn
================================================================================

  STATE 1 — PERCEIVE  [1 Gemini call, structured output]
    Input : user message + recent history + customer memory snippet
    Output: {
              emotion: {state, intensity},
              intents: [list],              // multi-intent supported
              entities: {order_ids, products, ...},
              tool_decision: {action_type, tools:[{name, args}]},
              needs_clarification: bool,
              clarification_question: str|null
            }

  STATE 2 — RETRIEVE  [no LLM call; parallel lookups]
    - Pull relevant policy/FAQ chunks from LightRAG (for the intents).
    - Traverse Neo4j for the referenced customer/order entities.
    - Pull short-term state + long-term customer memory.

  STATE 3 — DECIDE  [logic, uses STATE 1 output]
    - Route to: ANSWER | ACT | CLARIFY | CONFIRM | ESCALATE.
    - For ACT on irreversible ops (refund, cancel) -> route to CONFIRM first.
    - For multi-intent -> queue the actions.

  STATE 4 — ACT  [tool execution; no LLM call]
    - Execute queued tool(s) against mock biz APIs.
    - Write results back to Neo4j (status changes) + log to trace.
    - On tool failure -> fallback (retry once, else create ticket / escalate).

  STATE 5 — RESPOND  [1 Gemini call, generation]
    Input : retrieved knowledge + tool results + TONE DIRECTIVE (from emotion)
            + language directive (mirror Hinglish if user used it)
            + grounding instruction ("only state facts present in context;
              if unknown, say you'll check / escalate")
    Output: the final natural-language reply (streamed to UI).

  STATE 6 — REMEMBER  [no LLM call mid-session; summarize at session end]
    - Update short-term structured state (actions taken, open items).
    - On session end: 1 Gemini call to produce the long-term summary -> Postgres.

  Net LLM calls per turn: ~2 (PERCEIVE + RESPOND). Stays under free-tier limits.

  CONDITIONAL EDGES (LangGraph view):
    PERCEIVE -> (needs_clarification?) -> CLARIFY -> end turn
    DECIDE   -> (irreversible action?) -> CONFIRM -> end turn (await yes/no)
    DECIDE   -> (out of scope / failing?) -> ESCALATE -> handoff packet -> end


================================================================================
  8. TOOL / ACTION DEFINITIONS (agentic resolution)
================================================================================

Define these as Gemini function-calling schemas. Each maps to a mock biz API
and (where it changes state) a Neo4j writeback. Start with the starred ones.

  *check_order_status(order_id)            -> read; safe
  *get_refund_eligibility(order_id, item)  -> read; runs the graph+policy logic
  *issue_refund(order_id, item, amount)    -> WRITE; requires CONFIRM gate
   reschedule_delivery(order_id, new_date) -> write
   update_address(customer_id, address)    -> write
  *cancel_order(order_id)                  -> WRITE; requires CONFIRM gate
   track_shipment(order_id)                -> read; safe
  *create_ticket(customer_id, subject, body, priority) -> write; also the
                                             fallback when a tool fails
   escalate_to_human(session_id, reason)   -> emits the handoff packet
   lookup_policy(topic)                    -> thin wrapper over LightRAG

CONFIRMATION RULE: any tool that moves money or is irreversible (issue_refund,
cancel_order) MUST go through STATE 3 CONFIRM — the bot states what it's about
to do and waits for an explicit yes. This is both a guardrail and a trust signal.

Each tool returns a STRUCTURED result {success, data, error}. The RESPOND step
turns that into natural language with the right tone — it never makes up an
outcome the tool didn't return.


================================================================================
  9. OTHER ASPECTS (guardrails, security, errors, scale, testing)
================================================================================

9.1 GROUNDING / ANTI-HALLUCINATION
  - System prompt for RESPOND: "Only state facts present in the provided context
    (policy chunks, graph data, tool results). If the answer isn't there, say you
    need to check or escalate — never guess a policy, price, or outcome."
  - If LightRAG + graph return nothing relevant -> CLARIFY or ESCALATE, don't
    fabricate. A bot that invents a refund policy on stage is a demo disaster.

9.2 CONFIRMATION GATES
  - Money / irreversible actions require explicit user confirmation (Section 8).

9.3 SECURITY & PII
  - Never echo full payment details; mask (e.g., card ending 1234).
  - Mask PII in logs/traces. Keep secrets in .env (never commit). Provide
    .env.example in the repo.
  - Validate/sanitize tool arguments before hitting the mock APIs.

9.4 ERROR HANDLING & GRACEFUL DEGRADATION
  - Tool fails -> retry once -> else create_ticket + tell the user honestly +
    optionally escalate. Never leave the user with a raw stack trace.
  - LLM 429 (rate limit) -> exponential backoff, then a polite "one moment".
  - Neo4j / store unreachable -> degrade to LightRAG-only answers + flag.

9.5 RATE-LIMIT DISCIPLINE (free tier)
  - ~2 LLM calls/turn by design (Section 7). Don't add more without batching.
  - Backoff on 429s. Cache the LightRAG index between runs.

9.6 TESTING
  - Unit-test each tool against the mock DB.
  - Scenario tests: scripted conversations (the demo scenario in Section 12)
    asserted end-to-end. These also serve as living documentation.

9.7 SCALABILITY (talking point for the 25% Architecture score)
  - Stateless backend -> horizontally scalable; state is externalized.
  - Stores swappable (SQLite->Postgres, NetworkX->Neo4j AuraDB) without code
    changes if you keep a thin data-access layer.
  - Tools are modular -> new business actions = new function, no core changes.

9.8 CONFIG
  - .env for keys (GEMINI_API_KEY, NEO4J_URI/USER/PASS, DB_URL).
  - A single config module; no hardcoded secrets or URLs.

  12. DEMO PLAN (one scenario that shows off everything)
================================================================================

Scenario: "The angry double-charge customer who also needs an address change."
This single flow exercises every differentiator — script it, rehearse it, record it.

  1. Customer opens angry:  "I was charged TWICE for order 1234 and I'm furious.
     Also I need my delivery address changed, kuch toh karo."   (Hinglish + multi-intent + anger)
       -> Emotion layer detects anger -> calm, apologetic tone, no cheer.
       -> Multi-intent detected: [billing dispute, address change].
       -> Mirrors light Hinglish in the reply.

  2. Bot traverses the graph: order 1234 -> payments -> finds a duplicate charge.
       -> Grounded in real (mock) data, not guessed.
